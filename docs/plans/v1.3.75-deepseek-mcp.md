# v1.3.75 DeepSeek MCP Bridge — Design Plan

> **Status**: Design only. No implementation yet.
> **Target**: Enable DeepSeek to use MCP servers configured in Codian Settings.

## 1. Current State: Why DeepSeek Doesn't Support MCP

### How Codex Uses MCP

```
CodexAgentRuntime
  → CodexAppServerClient (spawns Codex CLI)
    → Codex CLI reads MCP server configs from Codian
    → Codex CLI connects to MCP servers internally
    → Codex CLI discovers MCP tools (tools/list)
    → Codex CLI calls MCP tools (tools/call) during tool loop
    → Results flow back as JSON-RPC notifications → StreamChunks
```

The MCP tool execution happens **inside the Codex CLI process**. Codian only provides server configuration. The CLI handles discovery, connection, and execution.

### Why DeepSeek Can't Use This

DeepSeekRuntime communicates directly with the DeepSeek API via HTTP. There is no intermediate agent process that could connect to MCP servers. DeepSeek only knows about tools defined in `DEEPSEEK_P1_TOOLS` (the OpenAI-format tool schemas).

**The gap**: MCP server configs exist in `McpServerManager`, but there is no bridge that:
1. Enumerates MCP tools from configured servers
2. Converts them to OpenAI-compatible tool definitions
3. Routes MCP tool calls through the ToolExecutor
4. Handles MCP connections, timeouts, and errors

## 2. MCP Discovery Design

### Current Infrastructure

- `McpServerManager.getServers()` returns `CodianMcpServer[]` — server configs with `enabled`, `disabledTools`
- `McpTester.testMcpServer(serverConfig)` connects to one server and calls `tools/list`, returning `McpTool[]`
- `McpTool` has `name`, `description`, `inputSchema` (JSON Schema)

### Proposed Discovery Flow

```typescript
// New: src/core/tools/mcpBridge.ts

async function enumerateMcpToolsForDeepSeek(
  mcpManager: McpServerManager
): Promise<DeepSeekToolDefinition[]> {
  const servers = mcpManager.getServers();
  const allTools: DeepSeekToolDefinition[] = [];

  for (const server of servers) {
    if (!server.enabled) continue;

    // Connect and list tools
    const result = await testMcpServer(server.config);
    if (!result.success || !result.tools) continue;

    for (const tool of result.tools) {
      // Skip explicitly disabled tools
      if (server.disabledTools?.includes(tool.name)) continue;

      allTools.push({
        type: 'function',
        function: {
          // Namespace: mcp__<server>__<tool> (same convention as Codex)
          name: `mcp__${server.name}__${tool.name}`,
          description: tool.description || `MCP tool from ${server.name}`,
          parameters: (tool.inputSchema as any) || {
            type: 'object',
            properties: {},
          },
        },
      });
    }
  }

  return allTools;
}
```

### When to Discover

- **Lazy discovery**: On first query after provider switch or server config change
- **Cache**: Cache tool list per server with a TTL (e.g., 5 minutes)
- **Invalidation**: Re-discover when `reloadMcpServers()` is called

## 3. MCP Schema Mapping

### OpenAI-Format Conversion

MCP tools use JSON Schema for input definitions. The OpenAI function-calling format also uses JSON Schema. The mapping is mostly direct:

```typescript
// MCP tool → OpenAI tool definition
function mcpToolToOpenAI(serverName: string, tool: McpTool): DeepSeekToolDefinition {
  return {
    type: 'function',
    function: {
      name: `mcp__${serverName}__${tool.name}`,
      description: tool.description || `MCP: ${serverName}/${tool.name}`,
      parameters: {
        type: 'object',
        properties: (tool.inputSchema?.properties as Record<string, unknown>) || {},
        required: (tool.inputSchema?.required as string[]) || [],
      },
    },
  };
}
```

### Edge Cases

- Tools with no `inputSchema` → empty `properties: {}`
- Tools with complex nested schemas → pass through as-is (DeepSeek/OpenAI handles them)
- Tools with very long descriptions → truncate to 1024 chars

## 4. MCP Tool Execution

### Execution Flow

```
LLM calls: mcp__eagle__search
  → executeDeepSeekToolCall()
    → case startsWith('mcp__'):
      → parse serverName, toolName from tool_call.name
      → find server config in mcpManager
      → check tool not in disabledTools
      → connect MCP client to server
      → client.callTool({ name: toolName, arguments })
      → return result as string
```

### Connection Management

```typescript
// Option A: Connect per call (simple, slower)
async function callMcpTool(serverConfig, toolName, args) {
  const client = await connectMcpClient(serverConfig);
  try {
    return await client.callTool({ name: toolName, arguments: args });
  } finally {
    await client.disconnect();
  }
}

// Option B: Connection pool (faster, more complex)
// Maintain persistent connections per server, reconnect on failure
```

**Recommendation**: Start with Option A (per-call connection) for simplicity. Optimize to Option B if latency is an issue.

## 5. MCP Permission Layer

### Risk Classification

| Category | Examples | Default Policy |
|----------|----------|----------------|
| **Read-only** | Eagle search, database query, file list | Auto-allow |
| **Write-safe** | Eagle tag edit, note creation | User confirmation |
| **High-risk** | HTTP POST, file deletion, shell exec | Deny by default (whitelist only) |

### Classification Mechanism

```typescript
// Server-level configuration
interface McpServerPermissionConfig {
  serverName: string;
  readOnlyTools: string[];     // auto-allow
  writeConfirmTools: string[];  // ask user
  blockedTools: string[];       // deny
  defaultPolicy: 'confirm' | 'deny';  // for unclassified tools
}
```

### User Confirmation Flow

Same as Write/Edit: call `context.requestApproval()` with tool name, description, and arguments. User sees the MCP tool name, server, and arguments in the approval dialog.

## 6. MCP Timeout / Cancel

```
Per-call timeout: 30 seconds (configurable)
Abort signal: from DeepSeekRuntime.activeAbortController
Transport timeout: 10 seconds for connection establishment
```

```typescript
const MCP_CALL_TIMEOUT = 30000;

async function callMcpTool(...) {
  const controller = new AbortController();
  const timeout = setTimeout(() => controller.abort(), MCP_CALL_TIMEOUT);

  try {
    const result = await client.callTool(
      { name: toolName, arguments: args },
      { signal: controller.signal }
    );
    return result;
  } finally {
    clearTimeout(timeout);
  }
}
```

## 7. MCP Rollback Hook

### What Can Be Rolled Back

| MCP Tool Type | Rollback? | Mechanism |
|---------------|-----------|-----------|
| Read-only query | Not needed | N/A |
| Eagle tag add | Yes | Eagle remove-tag API |
| Eagle folder move | Yes | Move back to original folder |
| External API POST | No | Irreversible — warn user before execution |

### Rollback Implementation

- MCP tools that support rollback should declare a `rollbackTool` in their metadata
- TransactionLog can be extended to record MCP calls alongside Write/Edit
- Undo for MCP calls is **best-effort** — not guaranteed

---

## 8. MCP Streaming

### Current Limitation

DeepSeek's tool execution is synchronous — the tool call completes fully before the LLM continues. MCP tools that return streaming results (e.g., long-running queries) would block the tool loop.

### Future Enhancement

- Support MCP tools that return async results
- Show "MCP tool running..." indicator in the UI
- Poll or use MCP notifications for progress updates

**Not in scope for v1.3.75.**

---

## 9. Read-Only MCP (Phase 1)

### Recommended First Phase

**Only enable read-only MCP tools.** This is the safest starting point:

1. Enumerate MCP tools from enabled servers
2. Filter to tools with known read-only semantics (Eagle search, database query, etc.)
3. Add to DeepSeek's tool definitions
4. Auto-allow execution (no user confirmation needed, same as Read/Grep)
5. Log all MCP tool calls

**Risk**: Minimal — read-only tools cannot modify vault files or external state.

---

## 10. High-Risk MCP (Phase 2+)

### Requires

- Tool-level permission configuration
- User confirmation for each write-capable call
- Rollback hook registration
- Connection pooling for performance
- Comprehensive error handling and logging

### Tools to Exclude Initially

- Any tool with `shell`, `exec`, `bash`, `command`, `run` in the name
- Any tool with `delete`, `remove`, `destroy` in the name
- HTTP/webhook tools (unless explicitly allowlisted)

---

## 11. Recommended Implementation Phases

| Phase | Scope | Risk |
|-------|-------|------|
| **P1 (v1.3.75)** | MCP discovery + read-only tool execution | Low |
| **P2** | Write-safe MCP with user confirmation | Medium |
| **P3** | High-risk MCP with whitelist | High |
