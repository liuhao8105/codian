# Codian 回复延迟优化设计

## 背景与事实

一次简单问候实际耗时约 22.7 秒，其中 App Server 启动约 0.3 秒，模型推理约 12.2 秒。当前运行时保存了 `thinkingBudget`，但没有把它传给 Codex App Server；同时每一轮都把完整固定规则包装进用户消息。Codex CLI 0.144.5 本机生成的 App Server 协议确认：`turn/start` 支持 `effort`，`thread/start` 和 `thread/resume` 支持 `developerInstructions`。

## 目标

1. 让界面选择的推理强度实际生效。
2. 把固定规则从用户消息移到原生开发者指令通道，稳定消息结构和缓存前缀。
3. 删除与 Codex 自带工具说明重复的长篇通用规则，同时保留 Obsidian、安全、路径、上下文、联网和媒体规则。
4. 不改变模型选择、附件语义、历史记录、MCP 按需启用和用户数据格式。

## 方案比较

### 方案 A：自动切换快速模型

短消息自动切换到轻量模型。延迟收益可能最大，但会在用户不知情时改变模型能力，并可能导致同一会话内行为不一致，不采用。

### 方案 B：自动删除历史或不附带当前笔记

可以减少上下文，但会改变用户对连续对话和笔记关联的预期，还可能丢失必要事实，不采用。

### 方案 C：修复协议参数并精简固定规则

保持用户选择和数据语义不变，同时消除未生效设置和重复提示词。风险可通过协议级单元测试和完整回归测试控制，采用此方案。

## 架构与数据流

`CodexAgentRuntime` 在每次查询时读取当前模型和 `thinkingBudget`。非 `off` 值作为 `effort` 发送到所有 `turn/start` 请求；`off` 不覆盖 Codex 默认值，避免发送未被模型支持的伪值。固定规则由 `buildSystemPrompt` 生成，在新线程和恢复线程时通过 `developerInstructions` 传递。用户输入保持原始 `<user_request>` 内容，不再嵌套一份固定规则。

`mainAgent.ts` 继续负责生成 Obsidian 专属规则，但删除 Codex 已自带的 Read/Edit/Bash、子代理、任务列表和 Skill 使用手册。保留强规则和自定义指令，并继续置于固定提示词末尾。

App Server 子进程以 Obsidian 仓库根目录作为工作目录，不再以 Codex CLI 安装目录作为工作目录，避免扫描无关的项目级配置。

## 兼容与错误处理

- 不新增设置字段，不迁移 `data.json`。
- `off` 继续表示不主动覆盖推理强度。
- 重建线程、MCP 卡顿恢复和子代理等待轮次都使用相同推理强度。
- 线程恢复时重新传递开发者指令，确保设置变更在下一轮生效。
- App Server 不支持字段时会由现有错误恢复路径反馈，不静默降级。

## 验证

先写失败测试验证 `effort`、`developerInstructions` 和纯净用户输入，再实现代码。随后运行单元/集成测试、类型检查、lint、生产构建、发布校验和依赖审计。安装前备份插件运行文件和 `data.json`，安装后重启 Obsidian，核对版本、文件哈希、设置哈希，并用短问候实测首字延迟和总耗时。
